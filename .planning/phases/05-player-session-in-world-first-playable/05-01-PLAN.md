<objective>
Make the player WALK AROUND (PLAY-04) and harden the teleport handshake (PLAY-02), by EXTENDING the Phase-3 subtick seam and the Phase-4 streamer — not rebuilding either. Today `applyInput` (server/subtick.go) is a documented STUB (`p.lastInputAt = in.At`) that never decodes position, and `p.center` is pinned to the Phase-4 default `{0,0}` so the ring never follows the player (walk past spawn → void). This plan fills `applyInput` to decode the four jar-confirmed `ServerboundMovePlayer*` layouts, updates the tick-owned player position, and — on a chunk-boundary crossing — calls a small `recenterRing` helper that moves `p.center`, resets `centerSent`, prunes `sentChunks`, and forgets the far columns. The existing `tickChunks`/`flushOutbound` already key on `p.center`, so re-centering re-streams the new ring automatically. It also gates movement on the confirmed teleport id (validate the echoed `ServerboundAcceptTeleportation` VarInt against an incrementing `awaitingTeleport`) and routes `ServerboundPlayerLoaded` as a no-op.

Purpose: PLAY-04 is the single largest new behavior of the phase — the gap between "client stands still" and "client walks around a world that follows it". PLAY-02's teleport gate prevents the join-time spawn fight (rubber-band). Both are tick-owned, single-owner work over existing seams.
Output: a filled `applyInput` (movement decode + position + re-center), a `recenterRing` helper, the `tickPlayer` position fields + `awaitingTeleport`, the `dispatch` teleport-id validation + PlayerLoaded no-op, and the jar-derived `world.ForgetLevelChunk` encoder. ZERO new dependencies.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Untrusted 26.2 client → tick (movement packets) | The client sends arbitrary movement/teleport-confirm packets. They cross into the tick via the bounded subtick buffer and are decoded/applied on the owner goroutine. Malformed payloads, forged teleport ids, position spoofing, and movement floods all originate here. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-5-01 | Spoofing | dispatch AcceptTeleportation — a forged/wrong teleport id confirming the gate | mitigate | Validate the echoed VarInt against p.awaitingTeleport; set confirmedTeleport ONLY on an exact match. A wrong id leaves the gate closed (movement stays dropped). Asserted by TestTeleportGate. |
| T-5-02 | Tampering | applyInput / ForgetLevelChunk — malformed or short movement payload | mitigate | Every Scan in applyInput returns on error WITHOUT mutating position (dispatch is already total/never panics, T-3-02). | T-5-03 | Spoofing | pre-confirm movement fighting the authoritative spawn (rubber-band) | mitigate | applyInput returns immediately while !p.confirmedTeleport, so movement the client sent before acknowledging the spawn teleport is dropped (vanilla handleMovePlayer parity). |
| T-5-04 | Tampering | huge/NaN coordinates in a movement packet | accept | Decoded into tick-owned floats; chunkCenterOf clamps to a column index (int32) and the needed-ring is server-clamped (serverViewDistance) regardless of where the player claims to be, so a wild coordinate cannot enlarge the request/send set. Real anti-cheat movement bounds are Phase 6 (ENT-02); for v1 the bounded ring is the structural control. |
