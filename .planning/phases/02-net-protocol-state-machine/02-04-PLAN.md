<objective>
Rewrite the stub `AcceptConfig` into the full ordered 26.2 Configuration sequence and reach Play with no silent kick (NET-04). The current stub sends only Registry Data + Finish and never reads the client's Acknowledge — three of the four documented config-state pitfalls. This plan implements the established vanilla order (Select Known Packs → drain client replies → Update Enabled Features → Registry Data [from the embedded 26.2 NBT built in Plan 02-03] → Update Tags → Finish → read Acknowledge), dispatches inbound config packets by ID in a loop (handling the new 26.2 CodeOfConduct gracefully), and emits a readable Config Disconnect on any failure. Because no published spec covers protocol 776, correctness is sealed by a CAPTURE-DIFF against a real vanilla 26.2 server plus a human sign-off — the only authoritative check that a real client enters Play instead of hanging at "Loading terrain…".

Purpose: NET-04 is the phase's whole reason for existing and its single hardest requirement. The flow is confirmed (bot/configuration.go is the authoritative wire reference); the payload is built (Plan 02-03); this plan assembles them in the correct order and proves it byte-for-byte against vanilla. The Acknowledge-read fix (Pitfall 3) and the no-silent-kick discipline (Pitfall 6 + NET-07) are the difference between "reaches Play" and "hangs forever".
Output: a rewritten AcceptConfig, an integration test over the net.Pipe harness with the fork's bot client, and a signed-off NET04-CAPTURE-DIFF.md.

<!-- VERIFIED this session against fork code + research. -->
- The full vanilla config order (stable 1.20.5 → 26.2, confirmed by bot/configuration.go + wiki + cross-search):
    S→C Select Known Packs [{minecraft,core,<ProtocolName>}]   (MUST precede Registry Data)
    C→S Select Known Packs echo                                 (the LOOP-EXIT key — always sent by a real client)
    C→S Client Information                                      (OPTIONAL — consume/no-op; NEVER a blocking precondition)
    S→C Update Enabled Features [minecraft:vanilla]             (Feature Flags)
    S→C Registry Data × N                                       (registrydata.WriteRegistryData — embedded 26.2 NBT)
    S→C Update Tags                                             (registrydata.WriteTags — present, never pack-sourced)
    S→C Finish Configuration
    C→S Acknowledge Finish Configuration                        (READ THIS before Play — the stub never did)
- Pitfall 2: Known Packs MUST come before Registry Data (it governs NBT omission). v1 sends full NBT regardless after sending Known Packs — omission is optional. Read the serverbound echo but send full NBT anyway.
- Pitfall 3 (the stub's bug): the current AcceptConfig returns right after Finish without reading ServerboundConfigFinishConfiguration → desync/kick. The rewrite MUST block on reading the Acknowledge before returning (which lets server.go call AcceptPlayer / enter Play).
- Pitfall 6: 26.2 added ClientboundConfigCodeOfConduct / ServerboundConfigAcceptCodeOfConduct. Do NOT send CoC for v1. In the inbound config loop, treat unknown/unhandled IDs (incl. CoC) as no-ops (log + continue) exactly like bot/configuration.go's default — never panic/return on an unexpected ID.
- Anti-pattern (research): NO rigid "read exactly N packets" loop. The client interleaves Client Information / KeepAlive / Pong unpredictably — loop and dispatch by packet ID, answering KeepAlive/Ping inline.
- FIRM LOOP-EXIT CONTRACT (W2 — prevents a TestConfigSequence deadlock): the Known-Packs drain loop EXITS on the Known Packs echo (ServerboundConfigSelectKnownPacks) ONLY. Client Information (ServerboundConfigClientInformation) is OPTIONAL: consume and no-op it if it arrives, but DO NOT make it a precondition for proceeding. VERIFIED: the fork's bot/configuration.go::joinConfiguration (the Task 2 test client) NEVER sends ServerboundConfigClientInformation — only bot/basic/info.go sends a Play-state one. If AcceptConfig blocks waiting for both the Known-Packs echo AND Client Information, TestConfigSequence deadlocks forever. After the Known-Packs echo is observed, proceed to Feature Flags → Registry Data → Update Tags → Finish. The actual gate to Play remains the blocking read of ServerboundConfigFinishConfiguration (the Acknowledge), unchanged.
- NET-07 discipline: any config failure → return ConfigFailErr{reason: chat.Text(...)} so server.go AcceptConn sends ClientboundConfigDisconnect with a readable reason. Never bare-close on a config error.
- Pitfall 7 (the verification): no published spec covers 776. The ONLY authoritative correctness check is a capture-diff of Ender's Configuration byte stream vs a real vanilla 26.2 server (cached jar sha1 823e2250…, JDK 25 available) for the same connecting client, plus confirming a real client reaches Play. This is why Task 3 is a blocking human-verify checkpoint.
- The Configurations type's registry field can be dropped/repurposed: AcceptConfig now sources registry data from server/registrydata (Plan 02-03), not from the embedded registry.Registries struct. Adjust the type/cmd-ender wiring accordingly (keep it building).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Untrusted client → config read loop | Inbound config packets (Client Information, Known Packs echo, KeepAlive, Pong, CoC accept, unknown IDs) are attacker-controlled and arrive in unpredictable order |
| Server config send → client registry validation | The client silently rejects a malformed/out-of-order Configuration; a wrong order or missing Acknowledge-read hangs at "Loading terrain…" |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2-06 | Tampering (data integrity) | Registry payload / sequence order → silent client reject | mitigate | Known Packs before Registry Data; Registry Data from embedded real 26.2 NBT (Plan 02-03); Update Tags present; Acknowledge read before Play. Sealed by the vanilla capture-diff (Task 3). |
| T-2-05 | Repudiation | Silent kick on config failure | mitigate | Every failure path returns ConfigFailErr → ClientboundConfigDisconnect with readable text (NET-07); never a bare close. |
| T-2-10 | Denial of Service | Unexpected/unknown inbound config packet (incl. 26.2 CodeOfConduct) crashing the loop | mitigate | Dispatch by ID; unknown IDs are no-ops (log + continue), never panic/return — the loop only exits on the Acknowledge or a read error. |
| T-2-11 | Denial of Service | Client never sends Acknowledge (hang) | accept | The blocking read on the Acknowledge is bounded by the conn read deadline / KeepAlive timeout (Phase 3 TICK-04 owns the timer); Phase 2 relies on the underlying conn read error to break the loop. Noted for Phase 3. |
</threat_model>
