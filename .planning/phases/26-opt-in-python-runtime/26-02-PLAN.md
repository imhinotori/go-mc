<objective>
Build the off-tick Python execution lane: when a discrete event fires for a `runtime="python"` plugin, submit the hook to a bounded ants pool (GIL-held, LockOSThread-pinned worker), run it OFF the tick goroutine, and rejoin the tick via a new `pythonHookReady` asyncResult on `asyncIn2` drained by `applyAsyncResults` on the owner — the exact `pathReady` discipline applied to plugin dispatch. The python plugin uses the SAME `register(event, fn)` concept as Starlark, routed by `manifest.Runtime`. Attempt 3.14 sub-interpreters (one per worker) for real parallelism; fall back to one serialized interpreter with the WHY cited if gopy@3.14 doesn't cleanly expose them.

Purpose: This is the load-bearing PLUGIN-06 behavior — "Python runs heavy plugins OFF-TICK, rejoining via the existing async seam, same register API." It reuses the proven `asyncIn2`/`submitOrDrop`/`pathReady` machinery rather than building a parallel mechanism.
Output: `server/async_python.go` (the plain-value rejoin, both builds) + `server/async_python_python.go` (the tagged off-tick submit) + `plugin/python/{register,dispatch,subinterp}_python.go` + the heavylogger testdata plugin + the off-tick + register-and-fire + sub-interp-or-serialized tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| off-tick worker → tick-owned state | A python hook runs on a pool goroutine; it must NOT touch tick state directly — only rejoin via asyncIn2 |
| GIL → OS thread | The worker must hold the GIL on a LockOSThread-pinned goroutine for the whole call (CPython per-thread state) |
| python hook runtime → tick budget | A runaway/slow python hook must not stall the tick |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-26-02 | Tampering (data race) | a python hook racing tick-owned state | mitigate | the worker computes off-tick over plain args; the ONLY tick-state touch is pythonHookReady.applyTo on the owner inside applyAsyncResults (the pathReady TICK-05 discipline); the result carries plain scalars, never a *py.Object or live pointer; covered by the -tags python -race job |
| T-26-07 | DoS | a slow/runaway python hook stalling the tick | mitigate | the hook NEVER runs on the tick goroutine — submitOrDrop to the bounded pluginPool; a saturated pool DROPS (drop-on-overload), the tick never blocks; size the pool small (sparse off-tick submits) |
| T-26-08 | Tampering (memory corruption) | OS-thread migration while holding the GIL | mitigate | gopy's Lock() calls runtime.LockOSThread(); CallHook does lock→call→Decref→Unlock as one unit on one goroutine (RESEARCH Pitfall 5); no Go channel/blocking op between Lock and Unlock |
| T-26-01 | Tampering/Elevation | gopy leaking into server/plugin-host default graph | mitigate | the cgo submit + CallHook live behind //go:build python / in plugin/python; server/plugin-host use the plain-Go PythonPlugin interface + a `...any` dispatch callback; the no-gopy-in-graph grep gates every task |
</threat_model>
