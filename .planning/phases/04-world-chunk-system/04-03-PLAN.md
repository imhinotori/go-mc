<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Untrusted client view/position → chunk send volume | A client's (eventual) requested view distance and its position-update rate drive how many chunks the server generates and sends. Unbounded => OOM / tick stall. |
| Off-tick worker → tick (ChunkResult/chunkReady) | Only the immutable result may cross; the tick is the sole mutator of ChunkManager + per-player sent-set. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-4-01 | Denial of Service | A client requesting a huge view distance => unbounded needed-ring => OOM/gen storm | mitigate | Server-clamped view distance (small FIXED radius for v1; any future client-supplied value clamped to [2, serverViewDistance]). The needed-ring is (2r+1)^2 — bounded by the clamp, never by the client. Asserted by TestViewDistanceClamp. |
| T-4-06 | Denial of Service | Position-update spam re-triggering chunk work every packet, stalling the tick | mitigate | tickChunks only requests chunks in stateEmpty (MarkLoading flips it) and flushOutbound only sends not-yet-sent Ready chunks — both idempotent over the bounded ring. Re-walking the same center is O(ring) cheap and issues no duplicate work; worker singleflight dedups any cross-player overlap. |
| T-4-05 | Tampering | A mutable chunk escaping the worker into the tick (data race) | mitigate | chunkReady carries the immutable world.ChunkResult; applyTo (on the owner) is the sole insert point; the tick is the only mutator of ChunkManager + sentChunks. Proven by the Docker -race gate (TestChunkReadyRejoin). |
| T-4-02 | Denial of Service | Duplicate gen requests from multiple players for the same chunk | mitigate | MarkLoading prevents the SAME tick loop from re-requesting; singleflight (Plan 04-02) collapses cross-player concurrent requests for the same key to one generation. |
</threat_model>
