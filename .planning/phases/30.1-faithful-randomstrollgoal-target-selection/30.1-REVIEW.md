The RNG-lockstep contract is **sound** — the draw stream is identical across the Go goal and both byte-identical `.star` copies (gate `nextInt(60)`, then `nextFloat()`, then 30 `nextInt` in x/y/z order), the runtime snap is genuinely RNG-free, and the `.star` copies are byte-identical (`diff` clean). ## Critical Issues

### CR-01: `wantLandMode` probability branch is INVERTED vs the jar bytecode

**File:** `server/ai_goals_passive.go:188` (and the mirrored claims at `:166-168`, `:179-180`; `server/stroll_snap.go:105-121`; `server/ai_mob.go:57-61`; `server/plugin_entity.go:877-883`; both `main.star:34-37,69-71,82-83`; `30.1-01-SUMMARY.md:94,104,148`)

**Issue:** I disassembled `WaterAvoidingRandomStrollGoal.getPosition`:
```
42: nextFloat()
51: fcmpl ; 52: iflt 67     // if nextFloat < probability -> goto 67
55..66: LandRandomPos.getPos(mob, 10, 7)        // fall-through: nextFloat >= probability
67..71: RandomStrollGoal.getPosition()          // == DefaultRandomPos.getPos(mob,10,7)
```
So the jar is: **`nextFloat() < probability (0.001)` → DefaultRandomPos (the RARE ~0.1% path); `nextFloat() >= probability` → LandRandomPos (the COMMON ~99.9% path).**

The Go code has the meaning of the flag reversed:
```go
g.wantLandMode = r.nextFloat() < g.probability   // WRONG: < probability is DefaultRandomPos, not Land
```
This sets `wantLandMode=true` (the LandRandomPos path) when `nextFloat < probability` — i.e. it labels the rare ~0.1% DefaultRandomPos roll as "Land". Every doc comment compounds the error: `ai_goals_passive.go:166` ("the COMMON path (≈99.9%) is DefaultRandomPos.getPos"), the `[VERIFIED javap ...]` citation at `:179-180` ("nextFloat() >= probability -> RandomStrollGoal.getPosition (DefaultRandomPos)"), and `30.1-01-SUMMARY.md:94` all assert the inverse of the actual bytecode. The COMMON path is LandRandomPos, not DefaultRandomPos.

**Why it is not observable today (but is still a BLOCKER):** `snapStrollWant` ignores `wantLandMode` entirely and always applies the LandRandomPos validation (`isOutsideLimits`/`isRestricted`/`isNotStable` → `moveUpOutOfSolid` → `isWater`/`hasMalus`). Since LandRandomPos IS the genuine ~99.9% common path, the always-snap behavior is correct for the common case and the oracle stays green. But `wantLandMode` is a stored-and-cited stub explicitly meant to drive the "deferred no-up-snap DefaultRandomPos branch" (`stroll_snap.go:119-121`). When that branch is implemented to read the flag, it will fire the no-up-snap path ~99.9% of the time and the up-snap path ~0.1% — exactly inverted — re-introducing the wedge for nearly every stroll. This violates the 1:1 mandate at the bytecode level and is a landmine for the next phase that reads the flag.

**Fix:**
```go
// nextFloat() >= probability -> LandRandomPos (common, up-snap path);
// nextFloat() <  probability -> DefaultRandomPos (rare, no-up-snap path).
g.wantLandMode = r.nextFloat() >= g.probability
```
And correct every comment (ai_goals_passive.go:166-168, the `[VERIFIED javap]` citation at :179-180, stroll_snap.go:105-121, ai_mob.go:57-61, plugin_entity.go:877-883, both .star, and the SUMMARY) to state: **LandRandomPos is the ~99.9% common path; DefaultRandomPos is the ~0.1% rare path.** Note the DefaultRandomPos path's rejects also differ from Land — verified from the jar: `DefaultRandomPos.generateRandomPosTowardDirection` rejects `isOutsideLimits || isRestricted || isNotStable || hasMalus` with NO `moveUpOutOfSolid` and NO `isWater`; the deferred branch must encode that, keyed off the corrected flag.

## Warnings

### WR-01: `maxBuildHeightY` off-by-one vs `Level.getMaxY()` in the snap bounds

**File:** `server/stroll_snap.go:50-59` (`moveUpOutOfSolid` loop bound), `:61-68` (`isOutsideLimits`); constant at `server/block_break.go:74-78`

**Issue:** The jar's `LevelHeightAccessor.getMaxY()` default is `getMinY() + getHeight() - 1` (disassembled: `getMinY; getHeight; iadd; iconst_1; isub`). For the overworld that is `-64 + 384 - 1 = 319`, the highest valid block Y. The reused constant `maxBuildHeightY = dimMinY + 384 = 320` (block_break.go:78) is off by one, and its comment falsely asserts `320 == ServerLevel.getMaxY()`. `moveUpOutOfSolid` (the jar passes `level.getMaxY()`) loops `for y <= maxBuildHeightY` → `y <= 320` instead of `y <= 319`; `isOutsideLimits` checks `by > maxBuildHeightY` → accepts `by == 320` though `isOutsideBuildHeight(320)` is true (`y > getMaxY()` with getMaxY=319). Not observable for a flat-world pig at Y≈64 (±7 vertical never approaches 319/320), but it is a real fidelity defect inherited and propagated by this phase, and the `block_break.go` constant likely conflates `getMaxY()` (inclusive 319) with `getMaxBuildHeight()` (exclusive 320).

**Fix:** Introduce a correctly-named constant for the snap, e.g. `const dimMaxY = dimMinY + 384 - 1 // 319 == Level.getMaxY()`, and use it for `moveUpOutOfSolid`'s `y <= dimMaxY` and `isOutsideLimits`'s `by > dimMaxY`. Audit whether `block_break.go`'s reject is against `getMaxBuildHeight()` (320, exclusive) or `getMaxY()` (319, inclusive) and split the two constants so the conflation cannot spread further.

### WR-02: `TestEntityRandFaithfulDrawOrder` is now a vacuous no-op for the stroll draw stream

**File:** `server/ai_random_test.go:67-99`

**Issue:** This is the dedicated faithfulness test for the goal draw ORDER — exactly what this phase changed. It was NOT updated for Phase 30.1 and is now stale on every axis: it draws the reference gate as `ref.nextInt(stroll.interval)` (raw 120, but canUse now draws `nextInt(reducedTickDelay(120))==nextInt(60)`); it omits the new `nextFloat()` probability draw entirely; it draws only `dx,dz,dy` (3 nextInt in the OLD x,z,y order, not 30 in x,y,z); and it reads `m.wantX/wantY/wantZ`, which `canUse` no longer sets (the target is committed by `snapStrollWant` in `serverAiStep`, never called here). It passes only because, for the fixed seed `0xABCDEF`, both the real `nextInt(60)` gate and the reference `nextInt(120)` gate are non-zero, so `used==false`, `(gate==0)==false`, the equality holds, and the `if used { ... draw-order assert ... }` body never runs. The test provides ZERO coverage of the new draw order — a draw-order regression (the bug class this test exists to catch) would not fail it.

**Fix:** Rewrite the stroll arm to (a) use `reducedTickDelay(stroll.interval)` for the gate, (b) draw `nextFloat()` after the gate, (c) draw 10×(x,y,z) in the new order and build the raw candidate set, (d) force the gate to land on 0 (use a seed whose first `nextInt(60)` is 0, or the `forceTrigger` seam) so the `if used` body actually executes, and (e) drive `serverAiStep`/`snapStrollWant` (with a world that has a solid floor) to assert the committed `wantX/Y/Z`, OR assert the raw candidate stash on the goal directly. As written it is dead coverage masquerading as a guard.

### WR-03: `navWantsPath` is dead code with a doc that contradicts the actual `has_path()`

**File:** `server/ai_mob.go:141-166`

**Issue:** `navWantsPath()` is defined but called nowhere (`grep` finds only its definition). Its doc claims it is "used by the plugin nav handle's has_path()", but `navHandle.hasPath()` (plugin_entity.go:817-834) reads `e.ai.hasTarget` directly, not `navWantsPath()`. The `active()` doc (navigation.go:186-194) further claims has_path keys off the REAL path state (not hasTarget) — contradicting the actual implementation. This looks like an abandoned alternative to the `markArrived` fix: the arrival re-roll was ultimately solved by `markArrived` clearing `hasTarget`, leaving `navWantsPath` as an orphan plus three mutually-contradictory comments about how has_path resolves.

**Fix:** Delete `navWantsPath` (and its doc block), and reconcile the `active()` / `hasPath()` comments so they describe the actual mechanism: `has_path()` reads `mobAI.hasTarget`, which is now cleared on arrival by `markArrived`. If the real-path-state semantics were intended, wire `has_path()` to `active()` and add a test; otherwise drop the misleading prose.

### WR-04: Perf-gate re-baseline widens caps ~100× — verify it is not masking a real plugin regression

**File:** `server/perf_gate_test.go:66-95`

**Issue:** The relative cap moved from ~7% to **350%** and the absolute from a few µs to **30000 ns**. The justification (the old baseline measured a wedged/idle pig that stopped re-rolling, so it made almost no Starlark calls; the faithful active pig legitimately draws 30 + a 30-arg `path_to` per stroll at ~2× cadence with continuous re-roll) is sound in direction — the prior baseline genuinely measured a bugged idle pig, and the new cost is required by the 1:1 mandate and is plugin-interpreter overhead the Go arm does not pay. The risk is that a 350% relative cap is now so loose it can no longer distinguish "faithful active pig" (~214-243% measured) from a future per-tick alloc storm. The cap is ~1.4× the measured peak, which is defensible, but the absolute cap (30000 ns ≈ 2.4× the ~12.7µs peak) combined with the documented high async-latency jitter means the absolute backstop is nearly inert.

**Fix:** Acceptable as-is given the documented measurements, but tighten the relative cap toward the measured peak (e.g. 300% rather than 350%) so it retains regression-detection power, and consider asserting on the per-stroll Starlark **allocation count** (the stable signal the file header already identifies: plugin allocs 10245 vs 3436) instead of wall-clock ns, which would be both jitter-immune and a sharper regression guard. Not a blocker — the gate still trips on a gross regression — but the current caps trade away most of their sensitivity.

### WR-05: `path_to` 30-float form hard-codes `landMode=false` while the Go goal passes the real flag

**File:** `server/plugin_entity.go:865-883`

**Issue:** The plugin commits candidates via `e.ai.setWantCandidates(cands, false)` — always `landMode=false` — while the Go-native goal passes `g.wantLandMode` (`ai_goals_passive.go:234`). The two arms therefore store DIFFERENT `wantLandMode` values into `mobAI` for the same RNG roll. Today this is observationally inert (the snap ignores `wantLandMode`), and the comment correctly explains it. But it means the Go and plugin pigs are NOT byte-identical in `mobAI.wantLandMode` — the moment any code (or the oracle observation struct) starts reading that field, the two arms diverge and the oracle breaks. Combined with CR-01's inversion, the plugin's hard-coded `false` is doubly wrong: the corrected Go value would be `nextFloat() >= probability` (true ~99.9%), so the plugin's constant `false` would mismatch ~99.9% of rolls once the field is read.

**Fix:** When CR-01 is fixed and the deferred branch is wired, pass the real mode across the boundary — the planned "31st float" carrying `wantLandMode` (the `.star` draws the same `nextFloat()` so it can compute the same bool). Until then, add an assertion or a comment-tracked TODO that `wantLandMode` MUST NOT enter the oracle observation while the arms disagree, so a future oracle change does not silently desync.
