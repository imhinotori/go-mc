<objective>
Deliver GEN2-02 — the cross-chunk worker seam, the single biggest architectural cost of v2. Split the `Generator` INTERFACE into a pure single-chunk `GenerateTerrain(pos)` (fill->surface->carve, status `carvers`) + a `Decorate(view *Neighborhood)` pass that runs once all 8 neighbors are carved, over a 3x3 read/write proxy, + a `Dims()` accessor the scheduler needs to size the proxy. Grow the `Worker` a staging map + a single scheduler goroutine that holds carved chunks, detects neighborhood completion, decorates each center over a `Neighborhood`, and emits the final immutable `ChunkResult` exactly once per chunk. This is exactly vanilla's `FEATURES requires CARVERS@radius1, blockStateWriteRadius=1` gating (jar-confirmed).

- **Split-Generate** (NOT the write-buffer alternative). The staging map + scheduler goroutine is the design.

The seam (staging/scheduler/Neighborhood/heightmap-update wiring) IS the deliverable and is what gets tested. The late-neighbor-write-after-emit question is EXPLICITLY DEFERRED to Phase 11+ — document it as a constraint, do not solve it.

**Interface vs concrete `Generate` (compile-safety, do NOT get this wrong):** the `Generator` INTERFACE carries `GenerateTerrain`+`Decorate`+`Dims` ONLY. `Generate(pos) *level.Chunk` STAYS a CONCRETE method on `*NoiseGenerator` and `*Superflat` (terrain+decorate-in-one, for tests/SpawnSurfaceY/single-chunk). <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| off-tick worker (scheduler goroutine) -> tick (via immutable ChunkResult) | The scheduler owns staging + all decoration; it hands each finished chunk to the tick as an immutable ChunkResult and retains it only as an un-writable neighbor (no-op Decorate writes nothing in Phase 10). The single-owner handoff is the safety property — a worker write to an already-emitted chunk is the race the v1 design forbids. |
| streamer (tick) -> worker requests | Chunk positions arriving on the bounded requests channel are server-clamped column coords; the auto-request of neighbors is internal + idempotent via the `requested` set + singleflight. No client input reaches the seam. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-05 | Tampering | a data race from decoration touching 9 chunks across goroutines, or concurrent staging-map access | mitigate | ALL decoration + the staging/requested maps run on a SINGLE scheduler goroutine (no locks); terrain stays parallel + footprint-guarded; the parallel->serial handoff is the w.carved channel. Proven by the Docker `-race` stress run (-count=10) over the 5x5 region. |
| T-10-06 | Tampering | breaking the immutable single-owner handoff (mutating a chunk after it is emitted to the tick) | mitigate | Phase 10's Decorate is a no-op (writes nothing), so emit-and-keep is safe by construction; a `decorated` flag prevents double-emit; the late-write-after-emit question is DOCUMENTED + deferred to the feature phase. The -race stress asserts no post-emit write. |
| T-10-07 | Denial of Service | the auto-request neighbor expansion spinning under the bounded-channel drop-on-full backpressure | accept | The `requested` set makes each neighbor request once; the bounded requests channel drops on full (existing backpressure) and the streamer re-requests next tick — convergence is validated by the 5x5 region test completing. | T-10-08 | Repudiation | a center emitted twice or never (lifecycle bug) corrupting the world view | mitigate | The emit-once + neighborhood-completion tests assert each requested center appears exactly once on Results() and only after all 8 neighbors are carved; the `decorated` flag + the all-9-carved guard enforce it. |
