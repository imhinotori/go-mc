<decisions>
## Implementation Decisions

### Root cause (jar-verified — javap/CFR over temp/cache/26.2-inner.jar)
`server/ai_goals_passive.go::randomStrollGoal.getPosition` returns a raw `e.y + dy`
(dy ∈ [-7..+7]) with NO ground-snap and NO walkability check. It also draws in the WRONG order
(dx, dz, dy) vs the jar.

Vanilla chain (`WaterAvoidingRandomStrollGoal` → `RandomStrollGoal.getPosition` →
`LandRandomPos.getPos(mob, 10, 7)` → `RandomPos.generateRandomPos(supplier, mob::getWalkTargetValue)`):
1. `RandomPos.generateRandomPos`: loop **10** times; each iteration calls the supplier for a candidate
   `BlockPos`, weights it via `positionWeightFunction.applyAsDouble(pos)` (== `mob.getWalkTargetValue`),
   keeps the highest-weight candidate (strictly `> bestWeight`, so the FIRST max wins ties). Returns
   `Vec3.atBottomCenterOf(bestPos)` (== blockX+0.5, blockY, blockZ+0.5), or null if all 10 were null.
2. Supplier (`LandRandomPos.getPos` lambda):
   a. `RandomPos.generateRandomDirection(mob.getRandom(), 10, 7)` — draws **xt = nextInt(2*10+1)-10**,
      then **yt = nextInt(2*7+1)-7**, then **zt = nextInt(2*10+1)-10**. ORDER IS x, y, z.
   b. `LandRandomPos.generateRandomPosTowardDirection(mob, 10, restrict, direction)` →
      `RandomPos.generateRandomPosTowardDirection(mob, 10, random, direction)` (home-restriction bias:
      only draws extra randoms when `mob.hasHome() && xzDist>1.0` — a v1 pig has NO home, so SKIP the
      home branch, zero extra draws) → `BlockPos.containing(xt+mob.getX(), yt+mob.getY(), zt+mob.getZ())`.
      Then reject (return null) if `GoalUtils.isOutsideLimits(pos, mob)` ||
      `GoalUtils.isRestricted(restrict, mob, pos)` || `GoalUtils.isNotStable(mob.getNavigation(), pos)`.
   c. `LandRandomPos.movePosUpOutOfSolid(mob, pos)` = `RandomPos.moveUpOutOfSolid(pos, maxY, isSolid)`
      then reject (null) if `GoalUtils.isWater(mob, pos)` || `GoalUtils.hasMalus(mob, pos)`.

### Faithful-scope simplifications (cite each in code)
- **No home/restriction** for a v1 passive pig: `mobRestricted` is false, the `hasHome()` branch in
  `generateRandomPosTowardDirection` never runs → ZERO extra draws there. Port the home branch as a
  documented `// pig has no home — vanilla skips this branch (zero draws)` no-op so the structure is
  visible and a future home-bound mob slots in.
- `isOutsideLimits` (world build/Y limits) and `isRestricted` (home leash) are FALSE for a flat-world
  pig — port them as cited guards that currently evaluate to the vanilla default, never bake away.
- `getWalkTargetValue` / `BlockPathTypes` malus: the pattern-map step pins the exact existing surface
  (the pathfinder already classifies nodes for A*). If a full `getWalkTargetValue` is too large, the
  faithful minimum is: weight = 0.0 for a walkable node (the default `PathfinderMob.getWalkTargetValue`
  returns 0 unless a `WALK_TARGET` memory/sensor is set, which a v1 pig has none) → with all weights
  equal at 0.0 and the strict `>` tie-break, the FIRST non-null candidate wins. CITE this so it becomes
  a real malus read when block-path-type malus lands.

### RNG lockstep (THE care item)
The new draw sequence (3 direction draws per candidate × up to 10 candidates, plus the existing
1-in-interval gate draw) MUST be added to BOTH:
- `server/ai_mob.go`/wherever `newPigAI` builds the Go-native stroll goal, AND
- BOTH `vanilla_pig/main.star` copies: repo-root `plugins/vanilla_pig/main.star` AND the
  `//go:embed`'d `server/assets/vanilla_pig/main.star` (boot-load source of truth).
IN THE SAME PLAN, same draw order, draws confined to the goal callback. The pig oracle
`TestPluginPigEqualsGoNativePig` must stay GREEN: the DRY oracle world still rolls the stroll gate,
but with the new candidate draws identical on both sides the streams stay byte-identical. If the
plugin pig expresses stroll target selection declaratively (not via raw draws), the plan must verify
the Go-native and plugin paths consume the SAME number of draws in the SAME order — run the oracle as
the gate, do NOT assume.
</decisions>
