<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin hook → tick goroutine | a registered hook now runs INLINE on the single-owner tick goroutine at each discrete seam; a runaway/panicking hook can stall or crash the tick (disconnecting everyone via stopped keepalive). |
| watcher goroutine → tick goroutine | the fsnotify watcher runs off-tick and must hand the new Manager across the tick boundary WITHOUT mutating live tick-owned state (TICK-05). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-22-01 | Denial of Service | a runaway hook stalls the tick | mitigate | host.Emit builds each thread via `starlark.NewThread` (step budget set — Plan 01); a runaway hook returns `*EvalError`, the tick continues. The existing `tickOnce` panic-recover is the backstop. |
| T-22-02 | Denial of Service | a hook panics and kills the tick goroutine | mitigate | host.Emit's per-hook `recover()`+log+continue (Plan 01) isolates the panic; `tickOnce`'s recover guard is the second net. |
| T-22-05 | Denial of Service | hot-reload mutates the live hook map mid-dispatch (torn read / data race) | mitigate | The watcher builds a NEW Manager off-tick and sends the POINTER on `pluginSwap`; the tick owner is the sole writer of `t.plugins` and swaps it on-thread between ticks (never mid-Emit). Proven by `TestReloadDuringDispatch` under -race. |
