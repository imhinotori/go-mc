### 🧟 ZOMBIE MOVEMENT — REVISIT WITH USER (the "veremos más a detalle después" item)
The user reported, in order, as each fix exposed the next layer: melee too fast → jitter/"tries to go back" → freezes short of target → doesn't follow from far → parks beside player → **180° spin** → **30° wobble** → **moonwalk** → **"parte mal luego camina bien"** (bad launch from standstill) → final "se mueve medio raro". ROOT CAUSE of ALL the walk-feel symptoms: our nav was a KINEMATIC step model (fixed displacement toward the waypoint, no momentum, yaw set instantly) — NOT vanilla's physics. The current state PASSES all 5 live bot tests, but the user still wants to eyeball it — **the residual is momentum overshoot on abrupt direction changes (14% sharp reversals in the teleport-heavy start-stop bot test), which is faithful (a real mob doesn't brake instantly) but should be human-confirmed.**

**The ported vanilla movement chain (all javap/CFR-cited, this session):**
- `PathNavigation.followThePath` → `navigation.go` node-advance: per-axis `maxDistanceToWaypoint = bbWidth>0.75 ? bbWidth/2 : 0.75-bbWidth/2` (NOT euclidean) + `shouldTargetNextNodeInDirection` corner-cut (dot-product; `canMoveDirectly` LoS is a cited stub). Kills the staircase wobble. Advances ONE node/tick.
- `MoveControl.rotlerp` → `rotlerpDeg` (ai_goals_passive.go): body yaw turns ≤90°/tick toward the node (was instant → 180° snap). `wrapDegreesF` = Mth.wrapDegrees(float). Head yaw = `setLookAt` ≤30°/tick, separate from body (melee no longer writes body yaw — two controllers were fighting).
- `LivingEntity.travelInAir`/`handleRelativeFrictionAndCalculateMovement`/`getFrictionInfluencedSpeed` + `Entity.moveRelative`/`getInputVector` → `navigation.go` movement: accelerate `e.vx/vz += forward(yaw) × frictionSpeed` where `frictionSpeed = getSpeed × (0.216/blockFriction³)`, `move(vx,vz)`, then `vx,vz ×= blockFriction(0.6)×airDrag(0.91)=0.546`. Terminal ≈ getSpeed×1.203 (zombie 0.23 → ~0.277 b/tick). getSpeed = speedModifier × MOVEMENT_SPEED; chase modifier = 1.0 (`meleeChaseSpeedModifier`).
- **Melee re-engage fix** (ai_goals_attack.go): re-path when nav has no active path AND (`!inReach` OR target moved at all `movedSqr>1e-6`) — fixed "parks beside a strafing player" (movedFar's ≥1-block gate missed close strafing).
- **FOLLOW_RANGE fix** (navigation.go requestPath): search box + visited budget now read the mob's FOLLOW_RANGE attribute (zombie 35), not a hardcoded 16 → zombie can path to a target it acquires up to 35 blocks (was frozen past 16).
