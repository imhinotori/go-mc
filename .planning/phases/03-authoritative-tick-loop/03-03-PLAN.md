<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Untrusted client connection → tick-driven GamePlay | A real connection now feeds the tick. Inbound is the attacker-controlled Intent stream; registration and dispatch must keep game state owner-confined. |
| AcceptPlayer (accept goroutine) → tick goroutine state | Player registration must cross to the tick owner as a message; AcceptPlayer must not mutate tick-owned state directly. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-03 | Tampering | Player registration mutating tick-owned state from the accept goroutine (data race) | mitigate | Registration crosses to the tick owner as a channel message (join/leave Intent or registration channel); AcceptPlayer never touches the tick's player collection directly. Enforced by the Docker `-race` gate on the integration test. |
| T-3-05 | Denial of Service | Keep-alive bookkeeping driven off the tick (stall → mass disconnect) | mitigate | KeepAlive.Run is started as its OWN goroutine in main(); AcceptPlayer wires ClientJoin/ClientTick/ClientLeft but the timers live on KeepAlive's goroutine, never gated on the tick. (Independence proven in 03-02.) |
| T-3-02 | Denial of Service | A connection's inbound flood stalling the tick via dispatch | mitigate | Inherits 03-01's non-blocking drainInbound + 03-02's bounded subtick buffer; AcceptPlayer adds no blocking work to the tick. The integration test confirms the tick keeps advancing (Stats() TPS stays live) while a connection is active. |
</threat_model>
