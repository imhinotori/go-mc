<objective>
Build the Registry Data payload — the single highest-risk piece of Phase 2. Extract the authoritative 26.2 registry content (currently only on disk in the GITIGNORED `temp/cache/26.2-datagen/.../data/minecraft/`) into a committed `server/registrydata/` package, embed it with `//go:embed`, convert it to network-format NBT, and provide `WriteRegistryData(conn)` + `WriteTags(conn)` helpers. This deliberately replaces the stale, client-side `registry/codec.go` struct (whose flat `Dimension` schema predates 26.2's nested `attributes`/`default_clock`) for the SERVER SEND path. Getting this wrong is the "Loading terrain…" silent-hang trap (Pitfall 1); getting it right is what lets Plan 02-04's Configuration sequence actually reach Play.

Purpose: NET-04's payload is the load-bearing risk. The research VERIFIED that `registry/codec.go::Dimension` is missing 26.2 fields and that the real schema (nested `attributes`, `default_clock`, etc.) lives in the datagen JSON on disk. Serializing the old struct yields a registry the client silently rejects. This plan isolates the payload so it can be built and round-trip-tested independently of the sequencing in 02-04.
Output: a committed, embedded 26.2 registry dataset (dimension_type, worldgen/biome incl. plains, damage_type, chat_type), JSON→network-NBT conversion, `WriteRegistryData`/`WriteTags` send helpers, and a round-trip test.
</objective>
