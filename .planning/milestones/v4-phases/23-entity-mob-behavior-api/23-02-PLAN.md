<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Starlark goal callback -> tick-owned mob/world state | A declared goal's tick/canUse callback runs ON the tick goroutine and reaches state only through the Wave-1 handles. The starlarkGoal is the boundary: it builds fresh handles per call, bounds the thread, and isolates errors. |
| Plugin load (declare_mob) -> the tick-read registry | declare_mob writes the registry ONLY at load (single-threaded, before the tick owns it); the tick reads it at spawn. No mid-tick mutation. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-06 | Denial of Service | A goal callback with an infinite loop hangs the tick | mitigate | starlarkGoal.tick builds the call thread via starlarkpkg.NewThread (the budget-bounded step counter, stepBudget) — a runaway callback returns a *EvalError, the tick continues. |
| T-23-07 | Denial of Service | A goal callback panics/errors and kills the tick goroutine (disconnects everyone) | mitigate | Per-callback error isolation in starlarkGoal.tick/canUse/start/stop (log + continue); the existing tickOnce recover backstop is the second line. TestGoalCallbackIsolation proves it. |
| T-23-08 | Denial of Service | The per-mob-per-tick interpreter storm (200 mobs x 20 TPS = 4000 calls/sec) | mitigate | The interpreter fires ONLY inside a RUNNING goal's tick, gated by goalSelector arbitration; an idle mob makes 0 calls (TestNoInterpreterWhenIdle). buildAIFromDecl adds the goal to the selector — it does NOT add an unconditional per-tick call. |
| T-23-09 | Tampering / data race | A live *Entity escaping via a handle stashed in a module global read off-tick | mitigate | The handle (Wave 1) stores an id, re-resolved on the tick goroutine; starlarkGoal builds FRESH handles per call. TestDeclaredMobRace (Docker -race) proves the declared-mob tick path is race-clean. |
| T-23-10 | Tampering | A declared mob spawned as a NEW wire entity id (breaks the client) | mitigate | The base-type resolver maps base_type to an EXISTING data/entity.Entity (pig/zombie/...); spawnDeclaredMob copies that type's wire id + dims. "Custom" is the behavior; the gate asserts e.typ==entity.Pig.ID. An unknown base_type errors at load. |
| T-23-11 | Denial of Service | Spawning unbounded custom mobs (mob-flood) | accept | The Phase-23 gate spawns via the test/debug seam spawnDeclaredMob (no plugin-facing rate-limited spawn builtin in scope — CONTEXT defers a plugin spawn builtin's cap). A future plugin-facing spawn path must respect the existing naturalSpawner CREATURE cap. Documented, not built. |
